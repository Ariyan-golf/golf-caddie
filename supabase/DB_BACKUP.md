# Supabase データベース バックアップ・復元手順

対象: Golf Caddie AI（GCA）本番Supabaseプロジェクト（Project ID: `csbqnlybbdvsdvijzkpz`）
想定利用者: 有島（非エンジニア）。Windows + PowerShellでコピペ実行。
頻度: 月1回程度、手動。

## 方針（最優先事項）

GCAにとって最も守るべきは「会員がそのまま使い続けられる状態」＝ログインできる状態を保つこと。
そのため、業務データ（ラウンド記録・スコア等、`public`スキーマ）だけでなく、
**ログインアカウントの実体（`auth`スキーマ、`auth.users`を含む）もバックアップの対象に含める。**

`public`スキーマだけを書き出す方法は、業務データは戻ってもユーザーが誰もログインできない
状態を作ってしまい、バックアップとして不十分と判断したため、今回`auth`スキーマも対象に加えた。

---

## 0. 事前準備（最初の1回だけ）

### 0-1. 追加インストールは不要

このPCには、GCAアプリの開発に元々必要な Node.js / npm が入っている
（`node -v` / `npm -v` で確認済み）。これがあれば、Supabase CLIを別途インストールしなくても、
`npx` というnpm付属の仕組み経由でそのまま実行できる。この方法を実際にこのPCで動作確認済み。

（参考: Supabase公式はWindows向けにScoopというツール経由のインストールも案内しているが、
実行ポリシーの変更や管理者権限まわりでつまずきやすいため、今回は採用しない。
npx方式のほうがインストール手順自体が不要で、有島にとって失敗しにくい。）

### 0-2. データベース接続文字列（パスワード付きURL）を控える

1. Supabaseダッシュボード（https://supabase.com/dashboard/project/csbqnlybbdvsdvijzkpz ）を開く
2. 左メニューの「Project Settings」→「Database」を開く
3. 「Connection string」の「URI」タブに表示される文字列をコピーする
   （`postgresql://postgres:[YOUR-PASSWORD]@db.csbqnlybbdvsdvijzkpz.supabase.co:5432/postgres` の形）
4. `[YOUR-PASSWORD]` の部分を、実際のデータベースパスワード（同じ画面で確認・再発行できる）に置き換える

**この文字列（パスワードを含む）は、GCAのリポジトリ内のどのファイルにも絶対に書き込まないこと。**
チャットやSlack等、記録が残る場所にも貼り付けないこと。次の手順で、自分のPCの中だけに安全に保存する。

### 0-3. 接続文字列をPCに安全に保存する（1回だけ）

以下の `REPLACE_WITH_PASSWORD付きの接続文字列` の部分を、0-2で用意した実際の文字列に置き換えてから、
PowerShellに貼り付けて実行する。

```
setx SUPABASE_DB_URL "REPLACE_WITH_PASSWORD付きの接続文字列"
```

実行後、開いているPowerShellの画面は一度閉じて、新しく開き直す（`setx` は次回起動時から有効になるため）。

これで、パスワードはWindowsのこのPC・このユーザーアカウントの中だけに保存され、
以後は「1. 毎月の実行手順」のコマンドをそのままコピペするだけでよくなる。

## 1. 毎月の実行手順（コピペ用）

新しいPowerShell画面を開き、以下をそのまま1ブロックで貼り付けて実行する。
（フォルダ作成・日付付きファイル名の決定・バックアップ実行までをまとめて行う）

初回実行時、npmから確認メッセージが出ることがあるが、`--yes` を付けているため
基本的には止まらずそのまま進む想定。

```
$backupRoot = "$env:USERPROFILE\GCA-DB-Backup"
if (!(Test-Path $backupRoot)) { New-Item -ItemType Directory -Path $backupRoot | Out-Null }
$date = Get-Date -Format "yyyyMMdd"
$schemaFile = Join-Path $backupRoot "schema_$date.sql"
$dataFile = Join-Path $backupRoot "data_$date.sql"
npx --yes supabase@latest db dump --db-url $env:SUPABASE_DB_URL --schema public,auth -f $schemaFile
npx --yes supabase@latest db dump --db-url $env:SUPABASE_DB_URL --schema public,auth --data-only -f $dataFile
Write-Host "バックアップ完了1: $schemaFile"
Write-Host "バックアップ完了2: $dataFile"
```

実行が終わると、`C:\Users\<ユーザー名>\GCA-DB-Backup\` フォルダの中に、
`schema_20260918.sql`（構造）と `data_20260918.sql`（データ）のように、実行日の日付が入った
2つのファイルができる。この2ファイルが今月分のバックアップ。

**重要:** このフォルダには今回からユーザーのメールアドレスやパスワードのハッシュ値など、
個人情報を含むデータが保存される。フォルダをクラウドの共有フォルダに置いたり、
他人と共有したりしないこと。PC自体にログインパスワードを設定しておくこと。

### うまくいかないとき

- `db.csbqnlybbdvsdvijzkpz.supabase.co` への接続がタイムアウトする場合は、
  0-2のダッシュボードで「Connection Pooling」タブの「Session」モードのURIに差し替えて、
  0-3をやり直す（ネットワーク環境によって直接接続が届かない場合があるため）。
- `npx` の実行中に「Ok to proceed?」のような確認が出て止まってしまう場合は `y` と入力してEnter。
- エラーメッセージに `permission denied for schema auth` のような文言が出た場合は、
  接続文字列のユーザー名が `postgres` になっているか（0-2でコピーした文字列そのままか）を確認する。

## 2. 復元手順

復元には2つの状況があり、難易度が大きく異なる。

### 2-1. 同じSupabaseプロジェクトの中で、一部データを元に戻したい場合（低リスク）

例: 誤ってラウンド記録の行を削除してしまった、など。**プロジェクト自体は生きている場合。**
この場合 `auth.users` はそもそも壊れていないので、業務データだけを戻せばよい。

これには `psql`（PostgreSQL標準のコマンドラインツール）が必要。復元が必要になった時点で
以下を追加インストールする（Scoopが必要になる唯一の場面。事前準備の時点ではインストール不要）。

```
irm get.scoop.sh | iex
scoop install postgresql
```

インストール後、バックアップファイルを流し込んで復元する（実行例。日付部分は戻したいファイル名に置き換える）。

```
psql "$env:SUPABASE_DB_URL" -f "$env:USERPROFILE\GCA-DB-Backup\data_20260918.sql"
```

このケースでは、`auth.users` の行は変更していないため、**全ユーザーは変わらずログインできる。**

### 2-2. Supabaseプロジェクト自体が失われ、新しいプロジェクトから作り直す場合（高難度・要開発者対応）

この状況は、有島お一人でのコピペ作業ではなく、**開発者（またはSupabaseサポート）に依頼して
一緒に対応することを前提とする。** 手順の全体像は次のとおり。

1. Supabaseで新しいプロジェクトを作成する
2. リポジトリの `supabase/migrations` フォルダ内のSQLファイルを、古い順に新プロジェクトの
   SQL Editorで実行し、テーブル構造を再現する（または `supabase link` → `supabase db push`）
3. 直近の `schema_YYYYMMDD.sql` ・ `data_YYYYMMDD.sql`（`auth`スキーマ分を含む）を、
   2-1と同様の方法で新プロジェクトに流し込む
4. アプリ側（Vercel）の環境変数、特に `LINE_CHANNEL_SECRET` を、**以前とまったく同じ値**で
   新環境にも設定する

`auth`スキーマの復元は、Supabase内部が管理するテーブル同士の依存関係（トリガーや内部カラム）が
絡むため、`public`スキーマだけの復元より失敗しやすい。ここまでの手順で理屈のうえでは
ログイン継続が可能だが、**実際にこの全体フロー（新プロジェクトへのauth復元）を最後まで
試したことはない。**そのため「絶対に成功する」とは言い切れず、いざという時は開発者と
一緒に、慎重に進めることを前提とする。

## 3. 復元後の状態（何が戻り、ログインできるかできないか）

| ケース | 業務データ（ラウンド記録等） | ログイン |
|---|---|---|
| 2-1: 同一プロジェクトへの部分復元 | 戻る | **全ユーザーとも問題なくログイン可能**（auth.usersは無傷のため） |
| 2-2: 新プロジェクトへのフル復元が成功した場合 | 戻る | メール/パスワードのユーザー、LINEログインのユーザーとも、**以前と同じ資格情報でログイン可能な見込み**（LINE_CHANNEL_SECRETを同じ値に設定している場合） |
| 2-2: 新プロジェクトへのフル復元のうち、auth部分の復元が失敗した場合 | 戻る（publicスキーマのみ成功していれば） | **ログイン不可。** 会員には申し訳ないが再登録（メールアドレスでの新規登録、またはLINEの再連携）をお願いすることになる |

一番下のケースが発生した場合、会員に対しては次のいずれかをお願いすることになる。

- メール/パスワードで登録していたユーザー: もう一度「新規登録」からアカウントを作り直してもらう
- LINEログインのユーザー: もう一度「LINEでログイン」を押して、再度連携してもらう
  （その場合、以前のラウンド記録との紐付けは自動では戻らない可能性がある）

## 4. バックアップに含まれるもの／含まれないもの

### 含まれるもの

- `public` スキーマの全テーブルの構造・データ（`profiles` / `rounds` / `shots` /
  `club_averages` / `course_holes` / `course_tees` / `green_centers` / `invite_codes` /
  イベント・コンペ関連・day_pass関連など）
- **`auth` スキーマ（`auth.users` を含む）の構造・データ**
  → メールアドレス、パスワードのハッシュ値、LINEログイン用の合成アカウント情報が含まれる

### 含まれないもの

- Supabase Storageに保存されたファイル → 現状GCAはStorageバケットを使用していないため、
  今のところ影響はない（将来ファイル保存機能を追加した場合は別途対応が必要）
- Supabase Edge Functions → 現状GCAでは未使用のため対象外
- Supabaseプロジェクトの設定（Auth Providerの設定、Redirect URL等）・
  Vercelの環境変数・LINE Developersコンソールの設定 → いずれもデータベースの外側にある設定の
  ため、このバックアップには含まれない。新プロジェクトを作る場合は、これらを手作業で
  設定し直す必要がある

### 個人情報の取り扱いについて（今回`auth`スキーマを追加したことに伴う注意）

このバックアップにはメールアドレスやパスワードのハッシュ値など、個人情報が含まれるようになった。
バックアップファイルの保存先（`GCA-DB-Backup`フォルダ）は、有島のPCの中だけに置き、
クラウドの共有フォルダや他人と共有する場所には置かないこと。

---

**この手順書の管理について:** このファイル自体には認証情報を一切含めていない。
接続文字列（パスワードを含むもの）は、0-3の手順でPC内の環境変数として保存するのみとし、
このリポジトリやチャットには絶対に貼り付けないこと。
